Each policy on this page is small and proves one rule. Every answer under it is real output from [the program at the end](#the-program), run against Strig 0.6.1. It takes a policy file, a user, a permission and a resource path, written from the most specific step to the broadest. For Node, run `node ask.mjs` where the commands say `cargo run --`.

## Permissions

A permission is a dotted key the catalog declares. The catalog also says where it can be granted (`on`), what grants it as a side effect (`implied by`) and what it needs first (`depends_on`). `kinds` lists the kinds of resource, and `broad org` names the widest step above them.

Bob has a grant for `document.edit` and none for `document.view`.

`g-edit` applied and was not enough: `depends_on` means the prerequisite has to be allowed on the same resource too.

Ana was granted `document.export`. She asks for `document.invoice.export`, which that permission implies.

`reason.permission` names the permission the grant was written for, not the one asked. A permission the catalog does not declare is denied; [Getting started](/docs/getting-started) shows it.

## Which grant wins

A grant sits on one step of the resource path and applies to everything under it. The path ends with an implicit `global`, and `rank` in an answer is the position of the deciding grant's step.

```text title="Path and rank"
document:spec   project:apollo   org:acme   global
rank 0          rank 1           rank 2     rank 3
```

When several grants apply, the strategy picks one. The default, `most_specific`, lets the grant on the closest step decide, and a `deny` beats an `allow` on the same step. An `allow` for one document and a `deny` for the whole project:

<Run case="w2" />

`g-edit` is on `document:spec`, at rank 0, so it beats the freeze for that one document. For `document:notes` only `g-freeze` applies.

Add `strategy deny_overrides` after `broad org` and ask about `document:spec` again.

<Run case="w3" />

The same two grants matched, and the verdict flipped. The strategy is one line of the policy:

| Strategy | The deciding grant |
| --- | --- |
| `most_specific` | On the closest step that has any grant; a `deny` first on that step. The default. |
| `deny_overrides` | A `deny` at any step. |
| `permit_overrides` | An `allow` at any step. |
| `first_applicable` | The first applicable grant in source order. |

## Why an answer came out that way

`reason.kind` gives the cause. Its values:

| `reason.kind` | It means |
| --- | --- |
| `grant` | A grant decided: `grant_id`, its `permission`, its `rank` and the `strategy` that picked it. |
| `no_applicable_grant` | Nothing applied. The answer is `deny`. |
| `unknown_permission` | The permission is not in the catalog. The answer is `deny`. |
| `missing_prerequisite` | The permission would be allowed, but one it `depends_on` is not. |
| `override` | An override answered before the grants, with its `name`. |

## Beyond the grant

Three more parts of the model act on the same grants. This page does not cover them.

| Part | What it does |
| --- | --- |
| Relations | A grant for `relation editor` applies to whoever holds `editor` on a resource, read from stored tuples. |
| Governance | A change to the grants is applied only if every invariant passes: no escalation, no lockout, your own rules. |
| Audit | With the `audit` feature, each change, applied or refused, becomes a record. |
