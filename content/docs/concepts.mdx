A Strig decision answers one question: may this subject do this permission to this resource? This page takes the question apart, so you can write your first policy. Every answer on it is real output from Strig 0.6.1. Pick a command, and the bench shows the case.

## The question

A request has three parts.

- **Subject.** Who asks: an id, roles (each one optionally limited to a place), principals and attributes. You build it from what you know about the caller. Strig does not look anyone up.
- **Permission.** A dotted key from the catalog, such as `document.view`.
- **Resource.** What is touched, written as a path of steps from the most specific to the broadest: `document:spec`, `project:apollo`, `org:acme`. A `global` step ends every path without being written.

The answer is a `Decision`: `effect` (`allow` or `deny`), `reason`, `matched` (every grant that applied) and `warnings`. When nothing applies, the answer is `deny`.

## Permissions

A permission is a dotted key that the catalog declares. The line that declares it also says where a grant of it can sit: `permission document.view on project, document`. A permission the catalog does not declare is denied, with the reason `unknown_permission`.

## Targets and broad targets

A grant has a target: the step of the path it sits on. `on project` matches whichever project is on the path, and `on document:spec` matches that one document. The position of the matching step is the rank, counted from the resource itself.

```text title="Path and rank"
document:spec   project:apollo   org:acme   global
rank 0          rank 1           rank 2     rank 3
```

`kinds` lists the kinds of step a grant can sit on. `broad org` adds a kind that any permission accepts, such as an organization or a tenant. `global` is always broad. A grant on any other kind is refused when the file loads.

`in org:acme` is the scope, not the target. It says the resource path must pass through `org:acme` for the grant to apply.

## Roles

A role is a name that grants can address. `role editor inherits viewer` gives editors whatever viewers hold. A subject holds a role everywhere or only inside a scope: `user:ana has role editor in project:apollo` holds for resources whose path goes through `project:apollo`.

A grant names who it is for with one of five matchers: `anyone`, `role <name>`, `user <id>`, `principal <id>` and `relation <name>`. A relation grant applies to whoever holds that relation on the step the target matched, read from stored tuples. This page does not follow relations further.

## Conditions

A grant can end with `when`, followed by a condition over `subject.*`, `resource.*` and `env.*` attributes. The grant applies only when the condition holds. Conditions compare values, test membership, combine with `and`, `or` and `not`, and can test text, lists, addresses and the time of day. The [policy language](/docs/policy-language) lists them.

## Time zones

<VersionBadge version="0.7.0" />

Office hours are local. `time_between` and `weekday_in` read UTC unless you give them an IANA zone with `tz`. The same condition, in the three syntaxes and in JSON:

```text title="Rules"
g-hours: allow role editor to document.edit on document when time_between "09:00" "18:00" tz "America/Sao_Paulo"
g-monday: allow role editor to document.view on document when weekday_in ["mon"] tz "Europe/Lisbon"
```

```json title="JSON"
{ "op": "time_between", "from": "09:00", "until": "18:00", "tz": "America/Sao_Paulo" }
```

- **The instant decides the local time.** Daylight saving time follows the zone's rules. A window inside the hour that a spring-forward jump skips never holds that day. The hour that a fall-back repeats holds on both passes.
- **Midnight and the date are local.** A window that crosses midnight (`"22:00"` to `"06:00"`) and the weekday both follow the local date.
- **An unknown name is refused when the policy loads**, with position and hint. A condition built without validation fails when evaluated, and an `allow` that errors never applies.
- **The trace shows the local time it used**, for example `12:30 America/Sao_Paulo (UTC-03:00)`.
- **Without `tz` nothing changes.** A policy that uses `tz` exports its JSON with `"schema": 3`, so a reader of schema 2 refuses it. See [Upgrading](/docs/upgrading).

The zone database is the default feature `tz` of the `strig` crate. It adds about 0.9 MB to the `.wasm` (2.70 MB to 3.58 MB, 657 KB to 785 KB gzipped). Build with `default-features = false, features = ["audit"]` to leave it out; a `tz` in a policy is then refused at load.

## Prerequisites

`depends_on` makes one permission require others: holding it means holding each listed permission on the same resource. `implied by` widens what a grant reaches. `depends_on` narrows what a grant is worth.

## Which grant decides

Several grants can apply to one question. The strategy picks the one that decides. The default, `most_specific`, lets the grant on the closest step decide, and a `deny` beats an `allow` on the same step. An `allow` for one document and a `deny` for the whole project:

| Strategy | The deciding grant |
| --- | --- |
| `most_specific` | On the closest step that has any grant; a `deny` first on that step. The default. |
| `deny_overrides` | A `deny` at any step. |
| `permit_overrides` | An `allow` at any step. |
| `first_applicable` | The first applicable grant in source order. |

## Reading the answer

The engine reaches a verdict in four steps:

1. An unknown permission is denied.
2. Overrides run in order, and the first one that answers decides.
3. A grant is a candidate when all of these hold:
   - its permission is the one asked, or one that implies it;
   - the resource path passes through its scope;
   - its target matches a step of the path;
   - its subject matches and its condition is true.
4. The strategy picks the deciding grant. With no candidate, the answer is `deny`. Then `depends_on` is checked, and a missing prerequisite turns an `allow` into a `deny`.

`reason.kind` says which step decided:

| `reason.kind` | It means |
| --- | --- |
| `grant` | A grant decided: `grant_id` (`grantId` in Node), its `permission`, its `rank` and the `strategy` that picked it. |
| `no_applicable_grant` | Nothing applied. The answer is `deny`. |
| `unknown_permission` | The permission is not in the catalog. The answer is `deny`. |
| `missing_prerequisite` | The permission would be allowed, but one it `depends_on` is not. |
| `override` | An override answered before the grants, with its `name`. |

`matched` lists every grant that applied, in source order, not only the one that decided.

## What Strig leaves to you

- **Who the subject is.** Strig reads the subject you pass and decides for it. In a browser, `PermissionClient` decides locally to shape the interface, and the server still decides on every operation.
- **Where grants live.** The engine holds configuration, and the grants arrive with each call. Governance returns the new grant set when a change passes its invariants, and you persist it. Removing expired grants from storage is a job of yours.
- **The clock.** You supply the instant of the decision. Without it, a grant with a validity window or a time condition never allows.
- **Anything it has no condition for.** There is no regular-expression condition. Custom condition functions and custom overrides exist only in Rust, not in the Node binding.
- **IO.** The core does no IO and needs no async runtime. Real time, transports and the HTTP server are separate crates.

Three more parts of the model act on the same grants, and this page does not cover them.

| Part | What it does |
| --- | --- |
| Overrides | Decide before the grants: an owner, a suspended account, a maintenance window. |
| Governance | A change to the grants is applied only if every invariant passes: no escalation, no lockout, your own rules. |
| Audit | With the `audit` feature, each change, applied or refused, becomes a record. |
